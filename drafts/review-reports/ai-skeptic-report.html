AS-002
Unguarded divide in incumbent_wage_change_pct survives only on an undocumented upstream invariant (prior AS-006, still unfixed)
code/02_descriptive_analysis/02d_matching_simulation.py:143-144 · Undisclosed Assumptions / Edge-Case
LOW
What Was Claimed
The context flagged this as previously-unfixed and asked whether it still stands. The expression computes an hours-weighted mean incumbent wage change: (((w1 - w0) / w0) * annual_hours * weight).sum() / (annual_hours * weight).sum() * 100, with no guard on either the per-row /w0 or the aggregate denominator.
What Was Found
Still unguarded — the code is byte-identical to the prior audit. Edge tests T1a/T1b confirm it returns nan silently (no exception) when a zero employer_wage row or an all-zero-weight sample is fed in. However, it is unreachable in the shipped pipeline: 01a:295 clips employer_wage = hourly_wage_epi.clip(lower=7.25), so w0 ≥ 7.25 > 0 for every row; and 01a filters earnwt > 0 and raises on an empty sample, so the denominator is strictly positive. The realized matching_simulation.parquet carries finite values (0.0 for rigid rows, −6.0 to −18.3 for flex rows). The risk is latent: a future refactor that admitted a $0 wage or an empty cell would silently emit nan into a statistic that feeds the incidence narrative, with no error to catch it. Downgraded from the prior framing to LOW because it cannot currently trigger; retained because the protective invariant is nowhere documented at the divide site.
How It Was Verified
Replicated the exact expression in temp/ai-skeptic-tests/edge_tests.py under synthetic edge inputs (numpy warnings both promoted and suppressed): w0=0 → nan, all-weights-0 → nan, normal → −9.2. Confirmed the 01a clip and earnwt>0 filter that protect it, and confirmed finite realized output in the parquet.
What to Check
  • Add a guard (e.g., np.divide(w1 - w0, w0, out=np.zeros_like(w0), where=w0 > 0)) and a fallback for a zero-weight denominator, or
  • Add an inline assertion/comment stating the reliance on the 01a wage floor and non-empty positive-weight sample.
AS-003
02d recomputes the policy target from the recipient file instead of reading the persisted org_target_wage.json
code/02_descriptive_analysis/02d_matching_simulation.py:65-67, 400 · Undisclosed Assumptions
LOW
What Was Claimed
The target wage is the single most important policy threshold. 01a computes it as 80% of the weighted median paid-hourly wage and persists it to data/processed/org_target_wage.json; 01h and 02e both read that JSON (falling back to cfg["ws_target_wage"]).
What Was Found
02d does neither. _recover_target(w) reverse-engineers the target from the recipient parquet as median(employer_wage + subsidy_hr / 0.80). This is algebraically correct for any recipient whose subsidy is positive and uncapped, and it will match the JSON in normal runs — but it is an undisclosed third way of obtaining the threshold, not robust to edge composition (e.g., if recipients were mostly floor-pinned the recovered median could drift from the true target). The other two stages use the authoritative source; 02d silently diverges from that convention.
How It Was Verified
Read _recover_target (02d:65-67) and its call site (02d:400); compared to the JSON-reading pattern in 02e:49-57 and the 01a persistence at 01a:282-290.
What to Check
  • Confirm _recover_target reproduces org_target_wage.json["target_wage"] exactly on the current data, then switch 02d to read the JSON with the same fallback the other stages use.

INFO
What Was Claimed
_load_and_adapt_org_panel computes salaried_hourly = weekly / hours and folds it into nominal_hourly = np.where(paidhour == 2, hw_canon, salaried_hourly) for non-hourly workers.
What Was Found

This is harmless (no wrong result) but is exactly the kind of un-pruned leftover an AI edit produces when it adds a restriction without removing the now-unreachable branch.
