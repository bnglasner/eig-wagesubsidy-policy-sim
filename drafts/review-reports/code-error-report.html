CE-001
NumPy array indexed by pandas index labels in _agg_by_group
code/02_descriptive_analysis/02a_descriptive_stats.py · Line 214–221 · Python
LOW
Problematic Code
02a_descriptive_stats.py:214
workers = workers[valid_mask]
net_income_delta = net_income_delta[valid_mask.values]   # positionally compacted
rows = []
groups = workers.groupby(col, observed=True)
for label, grp in groups:
    ...
    nd = net_income_delta[grp.index]   # grp.index are ORIGINAL labels, not positions
Why This Is Wrong
After net_income_delta = net_income_delta[valid_mask.values], the array is compacted to only the surviving rows (length = number of rows passing the mask), indexed 0..M-1 positionally. But grp.index holds the original DataFrame labels of workers (a subset of the 0..N-1 RangeIndex). net_income_delta[grp.index] then indexes the compacted array with the original labels. This is only correct when valid_mask drops no rows (so labels still equal positions). It works today because every educ_group/age_bin value falls inside _EDUC_ORDER/_AGE_ORDER and sex_label/race_ethnicity have no NaN (verified against hourly_workers.parquet, N=15,596). If a future extract introduces an out-of-list category (e.g. an "Unknown" education group) or an NaN, rows are dropped and the mismatch either raises IndexError or silently pulls the wrong worker's net-income delta into avg_net_income_gain.
Recommended Fix
workers = workers[valid_mask].reset_index(drop=True)
net_income_delta = net_income_delta[valid_mask.values]
...
for label, grp in workers.groupby(col, observed=True):
    nd = net_income_delta[grp.index.to_numpy()]   # index now aligns with the compacted array
Resetting the index after filtering (or using net_income_delta[workers.index.get_indexer(grp.index)]) keeps the array and the group labels aligned regardless of how many rows the mask drops.
CE-002
Fallback counter n_fallback double-incremented across ladder steps
code/02_descriptive_analysis/02a_descriptive_stats.py · Line 141–148 · Python
LOW
Problematic Code
02a_descriptive_stats.py:141
if schedule is None:
    schedule = _load_schedule("single_0c", state)
    n_fallback += len(grp_idx)
if schedule is None:
    schedule = _load_schedule(fkey, "TX")
    n_fallback += len(grp_idx)      # same group counted a second time
if schedule is None:
    schedule = _load_schedule("single_0c", "TX")
Why This Is Wrong
When the first fallback (single_0c / same state) is missing, n_fallback is incremented; if that lookup also returns None, the second branch runs and adds len(grp_idx) for the same group again. A group that falls through two ladder rungs is counted twice, so the printed "Used fallback schedule for N workers" warning overstates the count. This affects only a diagnostic message, never any output file, and does not fire on the current checkout (all 408 family×state schedules resolve on the exact match), so results are unaffected.
Recommended Fix
if schedule is None:
    schedule = _resolve_fallback(fkey, state)   # single ladder, count once
    if schedule is not None:
        n_fallback += len(grp_idx)
Increment the counter once, after the fallback ladder resolves, so each group contributes at most len(grp_idx).

Why This Is Wrong
main() calls simulate() six times (two wage modes × three beta values), and each call re-reads the entire pool Parquet from disk. The pool never changes across calls, so five of the six reads are pure redundant I/O (plus another read at line 320 for the band). This is a correctness-neutral efficiency issue — no results change — but it wastes disk time proportional to pool size on every run.
Recommended Fix
pool = pd.read_parquet(pool_path) if pool_path.exists() else None
for rigid in (True, False):
    for tag, beta in mcfg["beta"].items():
        r = simulate(w, beta, target, rho, entry_wage, rigid, pool=pool)
Read the pool once in main() and pass it into simulate() / _entrants_from_pool().

def wmed(v, w):
    v = np.asarray(v, float); w = np.asarray(w, float); ok = ~np.isnan(v) & (w > 0)
    if ok.sum() == 0: return np.nan
    v, w = v[ok], w[ok]; i = np.argsort(v); cw = np.cumsum(w[i]); return float(v[i][np.searchsorted(cw, cw[-1]*0.5)])

def wq(x, qq):
    i = np.argsort(x); cw = np.cumsum(wt[i]); return float(np.asarray(x)[i][np.searchsorted(cw, cw[-1]*qq)])
Why This Is Wrong
These weighted-quantile helpers pack four to five statements onto a single line with semicolons, mixing sort, cumulative-sum, and search steps. They are correct, but the density makes the weighted-median logic hard to audit — and both files define near-identical logic. This is a readability suggestion only; behavior is fine.
Recommended Fix
def weighted_quantile(values, weights, q):
    v = np.asarray(values, float)
    w = np.asarray(weights, float)
    order = np.argsort(v)
    cw = np.cumsum(w[order])
    return float(v[order][np.searchsorted(cw, cw[-1] * q)])
Extract one shared, line-per-step weighted-quantile helper and reuse it for both the median and the p25/p75 diagnostics.
