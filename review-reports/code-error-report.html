CE-001
Missing/zero-hours fallback fixes annual_hours but not subsidy_hours — subsidy silently NaN/0
code/01_data_preparation/01a_data_ingest.py · Line 339–366 · Python
MEDIUM
Problematic Code
code/01_data_preparation/01a_data_ingest.py:339
eligible["weeks_multiplier"] = wkstat_vals.map(WKSTAT_WEEKS).fillna(DEFAULT_WEEKS).astype(int)
eligible["annual_hours"]     = eligible["hours_epi"] * eligible["weeks_multiplier"]

# Guard: if hours_epi is missing, fall back to config default
fallback_hours_mask = eligible["annual_hours"].isna() | (eligible["annual_hours"] <= 0)
if fallback_hours_mask.sum() > 0:
    default_annual = cfg.get("ws_hours_per_year", 2000)
    ...
    eligible.loc[fallback_hours_mask, "annual_hours"] = default_annual

# ── 7. Subsidy calculation ──
SUBSIDY_HRS_CAP = cfg.get("ws_subsidy_hours_cap", 40)
eligible["subsidy_hours"] = (
    np.minimum(eligible["hours_epi"], SUBSIDY_HRS_CAP)   # <- still raw hours_epi
    * eligible["weeks_multiplier"]
)
...
eligible["subsidy_annual"]  = eligible["subsidy_hr"] * eligible["subsidy_hours"]
Why This Is Wrong
A paid-hourly worker is admitted to eligible on the basis of a valid hourly_wage_epi (which for hourly-paid rows equals HOURWAGE_CANON_NUM and does not depend on hours). Such a row can therefore carry a missing or zero hours_epi (e.g. an hours-vary/997 case the upstream RF imputer did not resolve). The fallback block repairs annual_hours for exactly these rows (setting it to the 2000-hour default), so baseline_income = employer_wage × 2000 is non-zero. But subsidy_hours is computed afterwards from the still-missing raw hours_epi: np.minimum(NaN, 40) × weeks = NaN (or 0 when hours are exactly 0). subsidy_annual is then NaN/0 for those workers. Because pandas.Series.sum() defaults to skipna=True, the affected rows are silently dropped from gross_cost_bn and avg_subsidy while their weight still counts in total_workers_mn and in the avg_subsidy denominator — understating program cost and the average subsidy. The presence of the annual_hours fallback shows the authors expect missing hours to occur, so the gap is a real inconsistency rather than a purely hypothetical one.
Recommended Fix
# Derive a single filled hours-per-week series, then use it for BOTH
# annual_hours and the capped subsidy_hours so the two stay consistent.
default_weekly = cfg.get("ws_hours_per_year", 2000) / DEFAULT_WEEKS
hours_filled = eligible["hours_epi"].where(
    eligible["hours_epi"].gt(0), other=default_weekly
).fillna(default_weekly)

eligible["annual_hours"]  = hours_filled * eligible["weeks_multiplier"]
eligible["subsidy_hours"] = (
    np.minimum(hours_filled, SUBSIDY_HRS_CAP) * eligible["weeks_multiplier"]
)
Compute the filled hours once and drive both annual_hours and subsidy_hours from it, so no eligible worker ends up with a non-zero baseline income but a NaN/zero subsidy. Alternatively, apply the same fallback_hours_mask repair to subsidy_hours before subsidy_annual is formed.
CE-002
_int() casts coerced values straight to int64 — raises on any missing code
code/01_data_preparation/01a_data_ingest.py · Line 215–216 · Python
LOW
Problematic Code
code/01_data_preparation/01a_data_ingest.py:215
def _int(col: str) -> "pd.Series":
    return pd.to_numeric(raw[col], errors="coerce").astype("int64")

out = pd.DataFrame({
    "year": _int("YEAR"), "month": _int("MONTH"),
    ...
    "statefip": _int("STATEFIP"), "marst": _int("MARST"),
    "nchild": _int("NCHILD"), "wkstat": _int("WKSTAT"),
    "relate": _int("RELATE"), "educ": _int("EDUC"), ...
})
Why This Is Wrong
errors="coerce" deliberately turns any unparseable/missing value into NaN, but .astype("int64") cannot represent NaN and raises IntCastingNaNError, aborting the whole load. This applies to every column routed through _int() (YEAR, MONTH, AGE, STATEFIP, MARST, NCHILD, WKSTAT, RELATE, EDUC). In the current sample-gated employed panel these columns are fully populated (IPUMS NIU is a numeric code, not a null), so the current run is unaffected — hence LOW — but the coerce-then-hard-cast pattern is fragile: a single missing code in a future extract would crash the adapter rather than surface a clean diagnostic.
Recommended Fix
def _int(col: str) -> "pd.Series":
    # nullable integer tolerates coerced NaN; downstream comparisons still work
    return pd.to_numeric(raw[col], errors="coerce").astype("Int64")
Use pandas' nullable Int64 (or explicitly .fillna(sentinel) before the cast) so a stray missing value degrades gracefully instead of aborting the pipeline. Note the FIPS map key type is unaffected — Int64 values still match the integer keys in FIPS_TO_STATE.
CE-003
_race_ethnicity treats every HISPAN > 0 as Hispanic, misclassifying "don't know"/"N/A" codes
code/01_data_preparation/01a_data_ingest.py · Line 168–169 · Python
LOW
Problematic Code
code/01_data_preparation/01a_data_ingest.py:168
def _race_ethnicity(race: float, hisp: float) -> str:
    if pd.notna(hisp) and hisp > 0:
        return "Hispanic"
    ...
Why This Is Wrong
Per the IPUMS CPS coding recorded in the dataset registry, HISPAN is 000 for not-Hispanic, 100–612 for specific Hispanic origins, and 901 ("do not know") / 902 ("N/A") for non-response. The predicate hisp > 0 classifies 901 and 902 as Hispanic, so any respondent whose Hispanic origin was not ascertained is silently coded into the "Hispanic" demographic bucket. The impact is small in a 2003+ basic-monthly universe (these codes are rare), and the identical pattern is used in 01h_nonemployed_pool.py, so the two stages remain internally consistent — hence LOW rather than higher.
Recommended Fix
if pd.notna(hisp) and 0 < hisp < 901:   # 901 = don't know, 902 = N/A
    return "Hispanic"
Bound the Hispanic test to the valid specific-origin range (100–612) so non-response codes fall through to the race-based branch. Apply the same fix in 01h to keep the two demographic derivations aligned.

Why This Is Wrong
Any STATEFIP not present in the 50-states-plus-DC map (historical combined codes 61–90, or "state not identified" 99) is silently reassigned to Texas rather than dropped or flagged. This differs from the employed path in 01a_data_ingest.py, which drops unmapped FIPS with a warning (lines 317–321). For a standard 50-state+DC extract there is nothing to remap so behavior is unchanged, but the fallback could quietly attribute non-employed population weight to TX if such codes ever appear. This line is outside the changed function (_find_raw_org_dir was the only edit in this file) — it is pre-existing and reported as INFO for author confirmation, not as a regression introduced by the internalization work.
Recommended Fix
# Match 01a: drop unmapped FIPS with a diagnostic instead of coercing to TX
org["state_code"] = org["STATEFIP"].map(_FIPS)
unmapped = org["state_code"].isna()
if unmapped.any():
    print(f"01h | [warn] dropping {int(unmapped.sum())} rows with unmapped FIPS: "
          f"{sorted(org.loc[unmapped, 'STATEFIP'].unique())}")

Confirm whether the "TX" fallback is intentional. Dropping (or explicitly logging) unmapped FIPS would make the non-employed pool consistent with the employed path and avoid a silent, geographically arbitrary reassignment.
CE-005
Vectorize the row-wise demographic derivations in the adapter
code/01_data_preparation/01a_data_ingest.py · Line 244–245, 326–329, 382 · Python
SUGGESTION
Problematic Code
code/01_data_preparation/01a_data_ingest.py:244
out["race_ethnicity"] = [_race_ethnicity(r, h) for r, h in zip(race, hisp)]
out["age_bin"]        = out["age"].apply(_age_bin)
...
eligible["family_type_key"] = [
    _family_key(int(m), int(n)) for m, n in zip(eligible["marst"], eligible["nchild"])
]
...
eligible["educ_group"] = eligible["educ"].apply(_educ_group)
Why This Is Wrong
These four derivations run a Python-level function once per row (list comprehension over zip or Series.apply) across the full ORG panel. They are correct, but on a multi-month panel of hundreds of thousands of rows the per-row Python call overhead is materially slower than a vectorized equivalent. This is a pure performance/readability improvement — correctness is unaffected.
Recommended Fix
# age_bin via pd.cut (vectorized, ordered)
out["age_bin"] = pd.cut(out["age"], bins=[-1, 24, 34, 44, 54, 64, 200],
                        labels=["16-24","25-34","35-44","45-54","55-64","65+"])

# race_ethnicity via np.select
is_hisp = hisp.between(1, 900)
out["race_ethnicity"] = np.select(
    [is_hisp, race.eq(100), race.eq(200)],
    ["Hispanic", "White, non-Hispanic", "Black, non-Hispanic"],
    default="Other, non-Hispanic",
)

# family_type_key via vectorized string ops
prefix = np.where(eligible["marst"].isin([1, 2]), "married", "single")
suffix = np.where(eligible["nchild"] >= 1, "2c", "0c")
eligible["family_type_key"] = prefix + "_" + suffix

# educ_group via map with default
eligible["educ_group"] = eligible["educ"].map(_EDUC_MAP).fillna("Unknown")
Vectorized pd.cut / np.select / map replacements eliminate the per-row Python calls and read more declaratively. (The np.select form also incidentally fixes the CE-003 901/902 edge via hisp.between(1, 900).)
